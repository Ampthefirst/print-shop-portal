# Print Shop Portal

Client portal for a custom CAD design and 3D printing business: clients create
accounts, submit orders, receive quotes, discuss the work, pay, and collect
their parts.

**Status:** Phase 1 of 13 — foundation. See the architecture plan for the full
build order and what is deliberately deferred.

## Stack

| Layer | Choice |
| --- | --- |
| Application | Django 5.2 (server-rendered) |
| Database | PostgreSQL 18 (Neon) |
| Styling | Tailwind CSS v4, standalone CLI — no Node toolchain |
| Static files | WhiteNoise |
| Hosting | Render |
| Python | 3.12 |

Later phases add Cloudflare R2 for file storage, Resend for email, Stripe for
payments, and the Google Calendar API for meeting links.

## Design rules

Three rules keep the free-tier-to-paid migration a configuration change rather
than a rewrite. They are not optional:

1. **Every environment-specific value comes from the environment.** No
   credential, connection string, or hostname is written into the source.
2. **No platform-specific APIs.** Nothing in the application knows it runs on
   Render. It is a standard Django process talking to Postgres over a URL.
3. **Real Postgres everywhere,** including local development. SQLite hides
   constraint and migration differences until they are expensive to discover.

## Local setup

Requires Python 3.12 and a Postgres connection string. The simplest source of
one is a dedicated development branch on the same Neon project used in
production — real Postgres, no local install, and no risk to live data.

```bash
py -3.12 -m venv .venv
./.venv/Scripts/python.exe -m pip install -r requirements.txt   # Windows
# source .venv/bin/activate && pip install -r requirements.txt  # macOS/Linux

cp .env.example .env
# then edit .env: generate a SECRET_KEY and paste your DATABASE_URL
```

Generate a secret key:

```bash
./.venv/Scripts/python.exe -c "from django.core.management.utils import get_random_secret_key as k; print(k())"
```

Build the stylesheet. The Tailwind binary is downloaded per machine and is not
committed:

```bash
curl -sSL -o tools/tailwindcss.exe \
  https://github.com/tailwindlabs/tailwindcss/releases/latest/download/tailwindcss-windows-x64.exe
./tools/tailwindcss.exe -i ./static/src/input.css -o ./static/css/site.css --watch
```

Run it:

```bash
./.venv/Scripts/python.exe manage.py migrate
./.venv/Scripts/python.exe manage.py createsuperuser
./.venv/Scripts/python.exe manage.py runserver
```

## Deployment

`render.yaml` describes the web service. `build.sh` installs dependencies,
compiles the stylesheet, collects static files, and applies migrations on every
deploy.

`DATABASE_URL` is the one variable set by hand in the Render dashboard, because
the database lives on Neon rather than on Render. `SECRET_KEY` is generated by
Render, and `RENDER_EXTERNAL_HOSTNAME` is supplied automatically and trusted by
`settings.py`, so the app works on the `onrender.com` subdomain and on a custom
domain without a settings change.

Moving off the free tier is a plan change in the Render dashboard; no code is
involved.

## Layout

```
config/           settings, URLs, WSGI
apps/core/        business configuration, health check
templates/        base layout and pages
static/src/       Tailwind input; output is generated, not committed
build.sh          Render build command
render.yaml       Render service definition
```

## Operations

- `/healthz/` returns 200 when the app and database are both reachable, and 503
  when the database is not. Render uses it as the health check path.
- `/admin/` holds the business configuration: business name, tagline, contact
  details, sales tax rate, delivery fee, and order limits. These are database
  values precisely so that changing them never requires a deploy.
